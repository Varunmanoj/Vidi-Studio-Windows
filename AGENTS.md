# VidiStudio Windows agent guide

Follow the shared [VidiStudio design system](../DESIGN.md). Use consistent icon meanings across platforms, with visible labels and accessible names. Every app-owned menu action, submenu and toggle needs a meaningful icon, including in Settings, dialogs and context menus. Run `python3 script/check_menu_icons.py` and the menu parity checks, then verify affected menus in the installed apps.

Update the shared [DESIGN.md](../DESIGN.md) in the same task whenever you change the app's design or interaction. Document the affected layout and behavior, availability, keyboard and screen-reader expectations, and platform differences.

Native WinUI 3 desktop application for Windows 10 version 1809+ (x64) and Windows 11+ (ARM64) in `Vidi Studio Windows.slnx`. `Vidi Studio Windows/` owns the native XAML UI, view models, and engine invocation. `engine/vidistudio_engine.py` owns all project processing, storage, and writes. `SpeechHost/` (`SpeechHost.csproj`) provides isolated speech synthesis across ARM64, x64, and x86. The sibling `VidiStudio Mac` repository is the reference desktop implementation; keep feature, export, and UI parity with Mac (`docs/FEATURE_PARITY.md`, `script/check-mac-export-parity.py`).

Project data lives in portable local folders with relative paths. Credentials live only in the user config outside projects. No Firebase, Firestore, authentication, or embedded website. Gemini runs only in the Python engine; keep API keys out of argv, logs, and project JSON.

Use Fluent Design System controls with theme-aware styling. Use high-contrast red (`#E52B32`) for the timeline scrubber thumb, active progress track, and thumbnail playhead handle. Maintain centered progress cards for active processing and exports. Preserve labels, keyboard shortcuts, visible focus, and UI Automation names for screen readers.

## Required Help and website documentation synchronization

- Keep the website's marketing pages distinct from documentation: explain the product, audience, accessibility value and benefits in plain language. Follow `../VidiStudio Online/AGENTS.md` → “Marketing pages must stay simple (required)”. Technical instructions, settings details, audio/timing figures and internal voice/storage names belong in Help and the website guide. Marketing uses “on-device local voices” and “API keys are securely stored”; Sarvam/ElevenLabs names and logos belong only in the dedicated online-voices section, with each provider's own-key requirement. Never copy implementation or release details into the landing page as a substitute for updating documentation.
- Starting with 1.0.356, both desktop Help windows display the published /docs website directly, including its images and navigation. Maintain current desktop instructions in `VidiStudio Online/src/pages/DocsPage.tsx` and the affected website references. A documentation-only update takes effect when the website is published and Help is reopened. Preserve stable chapter URLs, particularly `/docs#docs-8-exports`.
- Verify website navigation, search, and the website build for guide edits. For changes to the desktop Help reader, also verify the live page, offline message and recovery on both platforms. Record local and published results separately in `PROGRESS.md`.
- The HTML in `VidiStudio Mac/docs/help/` and its Windows-generated counterpart are legacy reference material. Use the existing Help generators for changes to those files. Publishing website documentation does not require regenerating them or releasing a desktop app.

## Required desktop menu synchronization

Mirror the Mac menu hierarchy as closely as Windows native conventions allow: shared File/View menus, Playback with Transcript Overlay and Summary Reading, and Project with Editor Sections, Segments, Analysis, and Narration. Any menu or context/action-menu item added, removed, moved, renamed, re-keyed, or re-gated on **either** desktop must include its counterpart in the same task. Match stable command IDs, hierarchy/order/separators, labels/dynamic titles, enabled/checked state, and behavior. `MainWindow.Menus.cs` is the Windows menu/shortcut/guard/dispatch source; reference Mac `KeyboardShortcuts.swift` and `VidiStudioApp.swift`. Menus and accelerators must share the same guarded action. Translate Command→Ctrl and Option→Alt, avoid reserved/conflicting combinations, and document OS-specific exceptions in both `docs/DESKTOP_MENU_PARITY.md` files. Run `python script/check_menu_parity.py` and `python -m unittest tests.test_menu_parity` in both desktop checkouts with the combined workspace present. Build and pre-commit scripts run the checker; standalone skips are not validated parity. Update the checker and `MainWindow.SmokeTest.cs` for new menu constructs; do not weaken parity tests or leave a new item only on one platform without a genuine OS-specific exception.

Build using `powershell script/build-windows.ps1`. UI smoke tests run via `powershell script/test-windows-ui.ps1`. Package inspection runs via `python script/verify-windows-package.py`. Python parity and engine tests run via `python -m unittest discover -s tests`.

## Installed app updates

When a Windows change also advances the Mac version, include the native Mac Safari, Share and Finder bundles in that release update. Follow the sibling Mac `AGENTS.md` extension signing, version/build, replacement installation and PlugInKit verification requirements; updating Windows version files alone does not validate or install the Mac extensions. Record platform installation blockers explicitly.

When registering or installing a new build, first remove the previously registered or installed package and any stale unpacked copies (for example old development MSIX registrations and earlier `bin` outputs), so Start, taskbar, and Search show one current Vidi Studio entry and one current app path. `script/build-windows.ps1` builds and packages but does not install; registering or installing the package is a separate step that must delete the old copy first. After installing, confirm `Get-AppxPackage` lists one current version and old build/install paths are gone, and record the result in `PROGRESS.md`.

Install on every version update. After bumping the version, do not stop at a package in `AppPackages` or `bin`: remove the previous package, register/install the new build on the Windows host, and confirm `Get-AppxPackage` reports the new version with only one entry remaining. A version bump is not complete until that install is done and recorded in `PROGRESS.md`.

App versioning between Windows (`Vidi-Studio-Windows`) and macOS (`VidiStudio Mac`) must always remain strictly in sync. Every app fix or new feature must automatically advance the app version across both platforms before build and validation; do not wait for a separate version-bump request. Run `python script/sync_version.py --bump` to atomically increment the patch version across both Windows (`<Version>` in `Vidi Studio Windows.csproj` and `Version` in `Package.appxmanifest`) and macOS (`MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in `VidiStudio.xcodeproj/project.pbxproj`). If editing versions manually, ensure both platforms are updated to the exact same version `1.0.X` (with Windows package `1.0.X.0` and Mac build number aligned). The build scripts (`script/build-windows.ps1`), pre-commit hooks, and parity tests (`tests/test_parity.py`) automatically run `sync_version.py --sync` to maintain version parity. Record the resulting user-visible version in `PROGRESS.md` with the change's validation evidence.

Record progress and release evidence in `PROGRESS.md`. Do not claim live Gemini or Mac validation without actually running those paths.

## Windows release and website publication (required)

When the user requests a new Windows desktop release, carry these steps through package verification, GitHub prerelease publication and live website verification in the same task. Honor any draft-only instruction or publication timing the user specifies. Follow the installed-app and version synchronization requirements above.

1. **Build and verify the installers.** Use the intended release source and synchronized version. Build Release x64 and ARM64 on Windows with the Visual Studio toolchain. Use `script/package-release.ps1` for signed direct-download MSIX files and ZIPs. Inspect both with `script/verify-windows-package.py`, verify the signer, version, runtime dependencies, ZIP integrity and SHA-256 checksums, and exercise the installed app and packaged engine on available hardware. Include installation notes. Describe self-signed Windows packages and unnotarized Apple Silicon DMGs as evaluation builds when applicable. For a coordinated Mac release, follow the sibling guide for packaging, signing and extension checks. See [desktop distribution](docs/DISTRIBUTION.md).
2. **Update the Microsoft Store draft.** Build separate x64 and ARM64 Store uploads from a staged copy using the verified Partner Center product identity and the [Store packaging procedure](docs/microsoft-store/README.md). Check that the packaged manifests use the default registry and AppData isolation and omit `unvirtualizedResources`. In the Vidi Studio submission's **Packages** section, upload both builds, save the replacements, and reopen the draft to verify the new versions, architectures and validation status. Keep the submission in draft, including when publishing GitHub. Update listing copy only when requested.
3. **Publish the GitHub prerelease.** Create or resume the `v<version>` draft in `Varunmanoj/Vidi-Studio-Windows` targeting the exact source commit. If the build source is still local, publish it on a versioned release branch. For a coordinated Mac release, do the same in `Varunmanoj/VidiStudio-Mac`. Attach the verified direct-download installers, installation notes and checksums. Check GitHub's uploaded asset sizes and SHA-256 digests. Publish as a **prerelease** using the signed-in GitHub browser or the authenticated CLI. Verify the published prerelease and test the actual public installer URLs from its assets without authentication.
4. **Deploy the download links.** After the public Windows x64 and ARM64 assets respond successfully, update their installer and release URLs in `../VidiStudio Online/src/config/desktopDownloads.ts`. Update the Mac entries when the matching Mac assets are published and verified. The shared config drives the landing page, `/download`, and the guide's installation links. Run `npm run lint` and `npm run build`, and check the affected links in preview. Push the website commit to `main` and wait for the Cloudflare Pages production deployment. Verify that the live landing and download pages serve the new URLs and that each destination downloads successfully.

Record the source commits, package versions and paths, architecture and runtime checks, GitHub prerelease links, Microsoft Store draft status, and production website deployment in `PROGRESS.md`.

## Concise application UI copy

Keep explanatory descriptions, workflow instructions, and detailed behavior guidance in canonical desktop Help and website documentation. Do not add instructional paragraphs, explanatory footers, or long descriptions to Settings, Project Settings, inspectors, or application dialogs (including Import, Export, Delete, and generation/review dialogs). Use concise control labels and necessary action buttons. Retain short errors, validation states, affected item/file counts, required legal notices, and essential confirmation details. Preserve accessible control names and icon-action tooltips, without putting long procedural guidance there. When behavior changes, update Help and website documentation instead of expanding the application UI copy.


## Required menu access for every new UI action

Every new UI action anywhere in this application—including text/icon buttons, toolbar/sidebar/inspector actions, toggles, pickers, navigation/view controls, and Settings/dialog actions—must have a corresponding context-appropriate menu entry in the same task. Menus must expose the same action, navigation destination, toggle or choice, checked state, dynamic title, availability and confirmations through the same guarded path and shared state. Scope entries to the active window, section, dialog and visible selection. Mirror shared entries on the other desktop and update parity checks, native smoke/regression coverage, Help and website documentation. Follow the workspace AGENTS.md section “UI Actions Must Be Available from Menus (Required)” and record any runtime validation blocker; a new UI control without its menu path is incomplete.

## Cross-platform UI layout parity (Required)

- Treat the Mac layout as the desktop reference. When adding or changing any Settings page, dialog, sheet, inspector or workflow on either desktop, inspect its counterpart and keep section hierarchy/order, concise labels, field alignment, related button placement, defaults, availability, confirmations and results as similar as practical on both platforms. Complete the counterpart in the same task; do not leave avoidable layout drift for later.
- Use compact, named groups and consistent spacing. At ordinary widths, put labels beside their fields and related buttons beside one another. Reflow only when the available width requires it. Keep multiline editors, previews and timing/data tables full width where that improves readability. Preserve native controls, focus, screen-reader names/landmarks and keyboard/menu access.
- Reuse the desktop's shared layout components: native grouped Form/Section and horizontal action rows on Mac; the common Settings row/card/action helpers and CompactDialogLayout companion-window route on Windows. Preserve control values, header metadata, events, enabled/checked states and cancellation behavior when changing presentation. Avoid hard-coded light backgrounds and fixed widths that clip on smaller windows or scaled displays.
- Native OS window chrome, file pickers, keyboard conventions, platform voice engines and actual licensing/tool differences are valid exceptions, not reasons for unrelated layout drift. Record material exceptions and the affected screen pairs in docs/DESKTOP_UI_PARITY.md on both desktops. Keep Help and website guidance synchronized.
- Run python3 script/check_desktop_ui_parity.py and python3 -m unittest tests.test_desktop_ui_parity in each desktop checkout with both repositories present. These build/pre-commit gates include mutation tests for grouped forms, adjacent actions, shared form routing, theme-aware cards and retained native geometry checks. Add/update coverage for every changed screen; do not weaken assertions to hide a regression.
- Validate changed screens in the installed native apps on both platforms, in light/dark appearance and ordinary/compact windows. On Windows, run the appropriate packaged -DialogsOnly, -GallerySettingsOnly and other affected script/test-windows-ui.ps1 suites separately. Assert rendered bounds/alignment, horizontal buttons when they fit, accessible names, scroll access, value persistence and native command/cancel results. On Mac use native UI tests or inspected native accessibility/screenshots; run the production segment-sheet geometry tests when its sizing changes. Source contracts and builds are not proof of visual parity. Record exact runtime coverage and any unavailable platform checks in PROGRESS.md; never claim a skipped native check passed.

## Browser extension releases

**Describe with Vidi Studio** has its own version in `BrowserExtension/manifest.json`. Advance it when releasing changes to the browser commands, URL rules, permissions, updater, or desktop handoff that require new browser code. Check handoff compatibility on desktop releases. Desktop-only changes, including editor and progress UI, keep the existing browser version. Keep both desktop versions synchronized using the normal version script.

Ship the current browser resources with each app. The Safari, Share and Finder native bundle versions, builds, entitlements and signing identities follow the Mac app. Preserve registration and enablement. Verify the Safari web manifest and both Chromium editions against the independent browser release. Preserve stable installed extension IDs and rebuild changed ZIPs at their existing names. The Mac app provides Contents/Resources/BrowserExtension. The packaged Windows app publishes changed files in %LOCALAPPDATA%\VidiStudio\BrowserExtension on startup. The app-managed Chromium edition reloads on a changed extension version. Store packages use browser store updates.

On a browser release, run shared URL and Safari Share tests, verify the installed commands and a live update in Chrome and Edge, and record tested versions, package paths, installation, registration, and store status in PROGRESS.md.

Keep exactly one current ZIP per browser in the browser release output folder. Use stable filenames Describe-with-Vidi-Studio-Chrome.zip and Describe-with-Vidi-Studio-Edge.zip. Validate replacements before removing earlier versioned VidiStudio extension archives. Safari has one embedded extension in the replacement Mac app.
