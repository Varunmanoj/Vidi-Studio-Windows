The engine handoff now operates via dual-channel transient execution:
- At rest on disk: `~/Library/Application Support/VidiStudio/config.json` (macOS) and `%APPDATA%\VidiStudio\config.json` (Windows) NEVER contain `apiKey`. `apiKey` lives exclusively in the macOS Keychain (`com.vidistudio.gemini-api`) and Windows Credential Manager (`VidiStudio/GeminiApiKey`).
- During engine execution: The app creates a short-lived temporary invocation configuration file (isolated per run with OS-protected permissions) that contains the runtime settings and API key, hands it to `VIDISTUDIO_CONFIG`, sets `VIDISTUDIO_API_KEY` in the environment, and immediately deletes the temporary invocation file as soon as the process terminates. Both frozen binaries and script-based engines now receive the API key reliably.

Speech helper rebuilds automatically; SAPI retries (2026-10-24, version 1.0.108): the user's ARM64 VM with NaturalVoiceSAPIAdapter v0.2.10 (ARM64) still showed the general voice message. Root cause on our side: Visual Studio builds only copied the prebuilt helper in `runtime/speech/<platform>`, which only `setup-windows.ps1` republishes, so the 1.0.107 helper fixes never reached the app. The app project now has a `PublishSpeechHost` target (before `PrepareForBuild`, incremental on `SpeechHost` sources, also an `UpToDateCheckInput`) that runs a separate `dotnet publish` process (Program Files `dotnet.exe` preferred) into that folder, exactly like `setup-windows.ps1`. A first attempt nested an `MSBuild` task with cleared environment variables; the user's build then failed (an empty `MSBuildSDKsPath` stops the nested build from finding the SDK), so the nested task was replaced by `Exec` and a failed publish now only warns and keeps the existing helper, because it must never block building or running the app. The helper now retries a failing or silent SAPI voice up to three times (0.8 s, 1.6 s), keeps its plain explanation on the first stderr line with retry notes after it, and the engine keeps the start of stderr rather than the end. An empty stderr (helper crash) is reported as "The speech helper stopped unexpectedly (exit code …)". Upstream, the add-on's online voices remain intermittent after Microsoft's 12 October 2026 service change (issue #120), so a VM is unlikely to be the cause; the README lists isolating steps (the add-on's TtsApplication.exe and log.txt). No menu or shortcut changes.
